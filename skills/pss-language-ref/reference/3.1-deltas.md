# What is new in PSS 3.1

Read this when the tool may implement 3.0, or when a tool rejects something this reference says
is legal. Every rule below is tagged **3.1** inline on its `lang/` page.

Source: *PSS 3.1 Draft for Public Review, August 31, 2026*. Where a construct is a refinement of
an existing one rather than wholly new, that is noted.

The **"The additions"** section below is structured to mirror the LRM introduction's own
"new features (by section number)" table, so the two can be diffed against each other when the
next revision lands. Two entries are **not** in that table and are marked *(not in the LRM's own
new-features table)*.

---

## Quick answer: "will this compile on a 3.0 tool?"

| If you wrote… | 3.0-safe? | Fallback |
|---|---|---|
| `soft` constraints | **no** | `default` value constraints, or restructure with `if`/`else` |
| **generic constraints** (`constraint c() {…}`, parameterized, or value-yielding) | **no** | a `dynamic constraint` for the no-parameter case; otherwise duplicate the constraint text |
| `mutable` component attributes | **no** | accumulate in a struct passed through the flow, or an imported solve function holding state |
| inline action attribute initialization `do A { .f = e };` | **no** | `do A with { f == e; };` |
| multidimensional action-handle arrays | **no** | flatten to one dimension |
| exec block tags | **no** | accept the duplication, or restructure so one object emits the block |
| **exported functions** (`export function …`) | **no** | an imported function calling back, or an exported *action* (§20.10) |
| `message()` in a solve exec | **no** | `print()` on the solve side |
| mustache in a **string expression** | **no** | `std_pkg::format()` |
| **control-flow directives / embedded comments in a triple-quoted string** (`{% … %}`, `{# … #}`) | check your tool | generate the text from a solve function instead |
| annotations (`@doc`, `@code_doc`, user-defined) | **no** | comments |
| `overlap` (behavioral coverage) | **no** — new keyword in §4.4 | express the scenario without an overlap operator |
| symbolic register names | **no** | address-handle mode (`get_offset_*`), which is unchanged |
| `mem_access_desc_s` parameters on access functions | **no** — the LRM states this argument is **not backward compatible** | omit them; defaults make most *source* uses compatible |
| `reg_sized_c` / `reg_base_c` generic register bases | **no** | per-type code instead of generic |
| target-time channels (`sync_pkg`) | check your tool | polling with `yield` |
| `instance` component references | check your tool | a plain (non-reference) component field |
| everything else on the `lang/` pages | yes | — |

If a tool rejects a **3.1**-tagged construct, that is expected: report it and offer the fallback.
Do not silently rewrite. If a tool rejects something *not* tagged here, see
`tooling.md` §"Tools also have plain grammar gaps".

## Deprecated in 3.1

Deprecated is not removed — existing models still parse — but do not write new code this way.

| Deprecated | Replacement | Clause |
|---|---|---|
| `dynamic constraint` | a **generic constraint** with no parameters. The `dynamic_constraint` grammar production is gone; `dynamic` remains a reserved keyword | §13.1.1 note, §13.1.2 |
| array properties `a.size`, `a.sum` | the methods `a.size()`, `a.sum()` | §7.9.2.4 |
| an unbraced single-item `compile if` branch | always brace the branch, even for one item | §19.2 (note under Syntax 89) |
| referring to `packed_s` / `endianness_e` / `sizeof_s` via `addr_reg_pkg` | `std_pkg` — tools must accept either spelling | §21.13.1, §21.13.2 (deprecated in PSS **2.1**, not 3.1) |

## The additions

### Solve-context string formatting — §4.7.1 → `lang/data/01-lexical-and-literals.md`

Triple-quoted strings with mustache expressions and control-flow directives may be used **as a
string expression**, not only as a target template. Expansion happens as part of evaluating the
expression, and anything referenceable in that context is referenceable in the mustache. A
triple-quoted string referencing only constant expressions is itself a constant.

The solve-platform output API itself (`format()`, `print()`) is §21.1.2.

### Inline action attribute initialization — §11.3.1.2 → `lang/activity/01-activities.md`

`do A { .f1 = expr };` passes data from an activity into a traversed sub-action. Evaluation
order within a list is unspecified; initializers may not mutate action-level attributes; called
functions must be side-effect-free; only fields accessible in `pre_solve` may be initialized,
from fields accessible in `post_solve`.

*Distinct from `with { f1 == expr; }`*, which is a constraint the solver must satisfy rather
than an assignment.

### `overlap` added to the keyword list — §4.4 → `lang/coverage/02-behavioral-coverage.md`

`overlap` is now reserved (Table 3), for the behavioral-coverage overlapping scenario operator.
Consequence beyond the feature itself: an identifier named `overlap` in a 3.0 model is now a
syntax error.

### Clarified and enhanced target templates and triple-quotes — Clause 4, Clause 20 → `lang/data/01-lexical-and-literals.md`, `lang/procedural/01-exec-blocks.md`

The LRM's introduction flags these clauses as "clarified and enhanced" without itemizing what
changed. What §4.7.1 now specifies, in three subclauses:

- **§4.7.1.1 Mustache notation** — `{{expression}}`; the expression shall be of scalar type; any
  function it calls shall be `pure`; the per-type conversion formats are listed here.
- **§4.7.1.2 Control-flow directives** — `{% if / else / else if / foreach / repeat %}`, closed by
  `{%%}`. Expressions inside a directive are not wrapped in mustache; the directives add no
  characters to the output.
- **§4.7.1.3 Embedded comments** — `{# … #}` and `{#}`, removed from the result.

Treat control-flow directives and embedded comments as tool-dependent on anything targeting 3.0.

### Target-time synchronization — §20.8, §21.9 → `lang/platform/02-sync-and-communication.md`

`sync_pkg`'s `channel_c<T, DEPTH>` with `get`/`put`/`try_get`/`try_put`, and the rule that a
target exec blocked on a channel operation does not stall other execs on the same executor.

### Multidimensional action-handle arrays — §11.3.2 → `lang/activity/01-activities.md`

Action-handle arrays may now be multidimensional, and a **sub-array** may be traversed as a
whole. Whole-array traversal still forbids inline constraints and initializer lists.

### Numeric expression evaluation — §8.7 → `lang/data/04-expressions-operators.md`

The rules for expression types, type propagation, and assignment-like contexts are stated
explicitly. This is largely a **clarification** of previously under-specified behaviour, but a
3.0 tool may differ in the corner cases — particularly result widths for shifts and `**`, and
signedness propagation.

### Mutable component attributes — §9.1.6 → `lang/structural/02-components.md`

`mutable` marks component data that may be modified during **solve-time** execution — solve
execs and activity solving — rather than being frozen after tree construction. It shall not be
modified from target execs. The qualifier propagates into aggregates, and may not be applied to
component instance fields.

*Why it matters:* accumulating state across repeated action executions previously had no
in-model expression.

### Soft constraints — §13.1.12 → `lang/constraints/01-algebraic-constraints.md`, `lang/constraints/README.md`

`soft expression;` expresses a prioritized preference that is discarded when contradicted.
Priority is positional: inline `with` blocks highest, then later declarations, containing scopes
over sub-attributes, flow-object outputs over inputs, derived types over bases, extensions over
initial declarations. `dist` is a soft constraint with **lower priority than all others**.

*Why it matters:* the pre-3.1 way to express a default was a `default` value constraint, which
can only be overridden statically. `soft` allows dynamic override.

### Generic constraints — §13.1.2, §13.4.11 *(not in the LRM's own new-features table)* → `lang/constraints/01-algebraic-constraints.md`

A **fixed** constraint always holds; a **generic** constraint holds only where it is referenced —
from inside another constraint, or traversed in an activity. Declared with a parameter list
(possibly empty): `constraint small_pkt_c() { pkt_sz <= 100; }`. Parameters may be `numeric` or
any data type, and may be `const`. A **value-yielding** form,
`constraint numeric max(numeric a, numeric b) (a < b) ? b : a;`, is usable anywhere an expression
of that type is legal. Recursion is permitted when gated by a non-random condition.

§13.4.11 extends relationship lookahead across them: a generic constraint traversed in an
activity holds for the rest of that branch and the remainder of the activity.

*Why it matters:* this is the **replacement for deprecated `dynamic` constraints**, plus the
first way to write a reusable, parameterized constraint. The LRM's introduction does not list it,
but §13.1.2 is new and §13.1.1 carries the deprecation note.

### Exported functions — §20.4.2 → `lang/procedural/04-foreign-interface.md`

`export [target|solve] function …` makes a PSS function callable from the foreign language.
Distinct from an **exported action** (§20.10), which infers a scenario per call.

### Exec block tags — §20.5.4 → `lang/procedural/01-exec-blocks.md`

A target-template exec block may carry a **struct-typed tag**; blocks of the same kind and
language with equal tag values are **coalesced at generation time**. Permitted on `header`,
`declaration`, `run_start`, `run_end`, and `exec file`; not on native execs, `body`, or solve
execs. Untagged blocks match nothing. Matching blocks whose generated text differs are an
**error**.

*Why it matters:* the standard answer to duplicated `#include`s and duplicated globals. Also
summarised on `lang/procedural/04-foreign-interface.md`, since it is the mechanism that makes a
target template safe to emit from many objects.

### `message()` on both platforms — §21.1.3 → `lang/platform/05-core-library-api.md`

`message()` is now declared unqualified, so it is available on the **solve** platform as well as
the target platform.

### Register base types — §21.14 → `lang/platform/04-registers.md`

**`reg_base_c` / `reg_sized_c<SZ>`** as explicit base components, exposing `get_handle()` and
the by-value access functions. This is what makes code generic over registers of a given
width (`list<ref reg_sized_c<32>>`).

### Annotations — §7.13, §21.6 → `lang/data/05-annotations.md`

User-declarable metadata attached to model elements: `annotation T { … }` declared in package
scope, applied as `@T {.field = const}`. Advisory — tools must ignore unrecognized annotations.
`std_pkg` defines the standard `doc` and `code_doc` annotations.

### Shared address claims — §21.11 (mode struct at §21.11.3) → `lang/platform/03-address-spaces.md`

`alloc_base_mode_s` with `access` (`EXCLUSIVE`/`SHARED`), `sharing`
(`RANDOM`/`OVERLAP`/`SAME_ADDRESS`), `skipping`, and `tag`, letting claims deliberately share or
overlap addresses instead of always being exclusive.

### Memory access descriptors — §21.13.9 → `lang/platform/03-address-spaces.md`

Access functions take an optional `mem_access_desc_s` parameter (defaulted), an **extensible**
struct for tool- or user-defined per-access metadata. Executor-based customization of
`addr_value()`, the primitive reads/writes, and the byte-list operations is specified in
§21.13.9.5. The LRM states explicitly that **this additional argument is not backward
compatible**.

### Symbolic register names — §21.14.6 → `lang/platform/04-registers.md`

`get_mnemonic_of_instance`, `get_mnemonic_of_instance_array`, `get_mnemonic_of_path`,
`set_mnemonic(prefix)`, and `use_symbolic_reg_names(grp, enable)`. Generated code can then refer
to registers by name rather than resolved address. The same one-of-two-schemes rule applies as
for offsets. Address-handle mode remains the default and is unchanged. §21.14.7 gives the
recommended packaging.

### Instance component references — §9.1.5.3 *(not in the LRM's own new-features table)* → `lang/structural/02-components.md`

The `instance` qualifier on component-reference fields, giving them the capabilities of
non-reference component fields — including use as an action-traversal context.

## What changed *between 3.1 drafts*

If the tool tracks an earlier 3.1 draft (this reference previously cited **Draft 19, July 14
2026**), the clause numbers moved. Content-wise:

- **Generic constraints (§13.1.2) were inserted**, renumbering all of §13.1 below member
  constraints by one. Soft constraints moved **§13.1.11 → §13.1.12**; the distribution directive
  moved **§13.1.12 → §13.1.13**.
- **§13.4.11 Lookahead and generic constraints** was inserted, moving `pre_solve`/`post_solve` to
  §13.4.12 and body blocks to §13.4.13.
- **§4.7.1 gained subclauses** `.1 Mustache notation`, `.2 Control-flow directives`,
  `.3 Embedded comments`.
- **§21.14 gained** `.6 Symbolic Register Names` and `.7 Recommended packaging`.
- `dynamic` constraints went from supported to **deprecated**, with the grammar production
  removed.

A tool tracking Draft 19 will not accept generic constraints.

## Known gaps in the LRM itself

Recorded so they are not mistaken for errors in this reference:

- **§4.4 Table 3 omits `soft`, `mutable`, and `annotation`**, although all three are 3.1 syntax
  the grammar requires. `INDEX.md` lists them marked †.
- **Example185 (§13.4.11) declares generic constraints without `()`**, which the BNF in §13.1.2.1
  requires. Written that way they would be *fixed* constraints. Follow the BNF.
- The **filename** of the public-review PDF says 2026.08.28; the document's own date line says
  **August 31, 2026**. This reference cites the document's date.

## Using this page

- **Writing for an unknown tool:** avoid the "no" rows in the quick-answer table, or state the
  dependency explicitly.
- **A tool rejected your code:** find the construct here. If it is listed, that is a version
  lag, not a bug in your model.
- **Reviewing someone else's PSS:** the presence of these constructs tells you the minimum tool
  version the model requires.
